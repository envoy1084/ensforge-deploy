# Rhinestone Sessions

The owner enables an on-chain session; a separate session key signs constrained ENS calls.
Rhinestone submits those signed intents through the deployed intent executor, which calls the HCA
and then the resolver. Sponsored execution requires no ETH or USDC on the session signer.

Apply the [Rhinestone 1.8.0 compatibility patch](/hca/installation#rhinestone-compatibility-patch).
Use the owner/SDK setup and resolver permission steps in [Execute with Pimlico](/hca/guides/pimlico)
first, then create this adapter instead of the Pimlico adapter.

## Prepare and enable a session

```ts
import { rhinestone } from "@ensforge/hca/rhinestone";

const sessionSigner = privateKeyToAccount(sessionPrivateKey);
const execution = rhinestone({
  profile: sepoliaHcaDeployment,
  chain: sepolia,
  owner,
  sessionSigner,
  sdk: { apiKey: rhinestoneApiKey },
});

const resolver = permissions.resolver;
if (!resolver) throw new Error("The name needs a resolver");

const session = await execution.extensions.sessions.prepare(sdk.config, {
  hca,
  resolver,
  validUntil: Math.floor(Date.now() / 1000) + 3600,
});
const enabled = await execution.extensions.sessions.enable(sdk.config, session);
const receipt = await publicClient.waitForTransactionReceipt({ hash: enabled.hash });
if (receipt.status !== "success") throw new Error("Session enablement reverted");
```

The owner pays for session enablement. Preparation checks the deployment generation and creates ENS
permissions for the selected resolver and registration flow; it is not arbitrary smart-account access.
Keep the same session key, expiry, salt, permission ID and enable transaction hash when recovering
work. Store a protected signer reference, never the private key, in workflow storage.

## Execute on the same chain

```ts
const submission = await sdk.hca.executeHcaCalls({
  hca,
  authorization: {
    kind: "session",
    permissionId: session.parameters.permissionId,
    enableTransactionHash: enabled.hash,
  },
  execution,
  calls: [
    sdk.records.setText.call({ name, key: "description", value: "Updated through an HCA session" }),
  ],
});
const outcome = await sdk.hca.waitForHcaExecution({ submission, execution });
```

Check `outcome.status` and reconcile an unknown result using the saved submission. Multiple supported
calls can share a batch. The adapter reviews the exact batch and checks signatures against the
on-chain validator before submission; a provider quote cannot silently add source approvals or swaps.

## Expiry and revocation

An expired or revoked session cannot authorize new calls. Enable a replacement explicitly and update
the workflow authorization through [resumeHcaRegistration](/sdk/api/hca/resume-hca-registration).
To revoke sessions, send an owner transaction:

```ts
await sdk.hca.revokeHcaSessions({ hca });
```

This revokes **all HCA sessions**, not just the session used by this example. Cancelling local work
or deleting storage does not revoke an on-chain session.

## Funding and release limits

Use sponsored execution for this release. Token-paid Rhinestone refunds remain unsupported because
hosted quotes currently include incompatible funding or approval requirements. More USDC does not
resolve that mismatch; the adapter deliberately rejects these quotes before signing.

For cross-chain funds, use [Independent cross-chain funding](/hca/funding), wait for destination funds,
then run ordinary registration or supported single-chain execution. Bridging and session execution
are separate operations with separate tracking and fees.
